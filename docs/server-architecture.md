## 1. Обзор системы

Сервер обрабатывает поток клиентских команд для множества независимых игровых сессий. Ключевые нефункциональные требования: минимальная задержка входа пакета, монопольная обработка команд одной игры (строгая согласованность), масштабирование по ядрам CPU без потери сообщений, управляемая остановка без потери данных.

Топология конвейера:

```
клиенты (HTTP POST/GET JSON)
   |
Endpoint (аутентификация, лимиты, поверхностный парс, маршрутизация)  — контур AP
   |
Первичный роутер (кодогенерированный O(1) диспетчер + таблица решардинга)
   |
Thread-safe Queue (по одной на рабочий поток, bounded, Channel-based)  — единственная точка синхронизации
   |
Рабочий поток (вторичный роутер -> планировщик Priority+Round-Robin)   — контур CP
   |
Game (Scope + Game Queue), по N игр на поток
```

Баланс CAP: внешний контур отдаёт приоритет доступности — `Endpoint.Accept` выполняет только дешёвые операции (парс заголовка, проверка подписи, лимит, запись в очередь) и никогда не блокируется надолго; внутренний контур отдаёт приоритет согласованности — все команды одной игры исполняются последовательно на одном потоке, что исключает состояние гонки внутри игрового мира.

Разделение уровней абстракции: домен (`GameServer.Games`) не знает о транспорте; транспорт (`GameServer.Endpoint`) не знает о правилах игры; синхронизация сосредоточена только в `GameServer.Messaging` и межпоточных акторах (`Resharding`).

## 2. Модель Акторов

Каждый актор при обработке очередного сообщения вправе выполнить ровно три операции из формального определения: изменить собственное состояние, создать конечное число дочерних акторов, отправить асинхронное сообщение без ожидания ответа.

Реализованные акторы и их состояния:

| Актор | Собственное состояние | Тип сообщений | Файл |
|-------|----------------------|----------------|------|
| `Game` | `Scope` (словарь объектов), `GameCommandQueue` (FIFO + флаг запечатанности), флаг await с меткой времени, приоритет | команды `ICommand`, десериализованные из `InboundMessage` | `Games/Game.cs` |
| `GameWorker` | карта получателей `IGameRecipient`, карта миграций, флаг глобального запечатывания, флаг финального снимка | `InboundMessage` (клиентские и управляющие) | `Workers/GameWorker.cs` |
| `GameProxy` | идентификатор игры, целевой писатель, обработчик переполнения | `InboundMessage` на пересылку | `Resharding/GameProxy.cs` |
| `BackupTransitThread` | собственная transit-очередь | конверты `TransitEnvelope` | `Resharding/BackupTransitThread.cs` |
| `Endpoint` | без изменяемого состояния (stateless) | строки запроса | `Endpoint/Endpoint.cs` |

Гарантия однопоточности актора: никто, кроме потока-владельца, не изменяет состояние `Game` и `GameWorker`. Перенос владения возможен только через формализованную процедуру миграции (раздел 11), которая атомарно заменяет получателя в карте источника после снятия снимка.

## 3. Доменная модель

### 3.1 Scope

`Scope` — объектная обёртка над словарём `string -> IGameItem`. Контракт `IScope`: `GetItem`, `Register`, `Unregister`, `Contains`, `ItemIds`. Ошибки: неизвестный идентификатор — `KeyNotFoundException`, дубликат — `InvalidOperationException`, пустые/пробельные идентификаторы — `ArgumentException`. Словарь обычный `Dictionary` — синхронизация запрещена инвариантом однопоточности (ТЗ 2.3).

`GameItem` — универсальный игровой объект с доступом к свойствам по имени (`GetProperty`/`SetProperty`/`PropertyNames`). Аналог UObject из курса: доменные типы (корабль, торпеда) задаются строкой `Type`, пространственные характеристики — значениями `Vector`.

### 3.2 Конвейер создания объекта (ТЗ 2.2)

Создание — не монолитный конструктор, а детерминированная последовательность из четырёх команд-модификаций:

| Шаг | Команда | Эффект |
|-----|---------|--------|
| 1. Память и регистрация | `CreateGameItemCommand` | `Scope.Register(itemId, new GameItem())` |
| 2. Доменный тип | `AssignGameItemTypeCommand` | свойство `Type` |
| 3. Позиция | `SetGameItemPositionCommand` | свойство `Position` (Vector) |
| 4. Скорость | `SetGameItemVelocityCommand` | свойство `Speed` (Vector) |

Композиция — `CreateGameItemPipeline.Build()` возвращает `MacroCommand`. Клиентский путь: команда `CreateItem` JSON -> `JsonServerCommandDeserializer` -> стратегия IoC `Games.CreateItem` (`RegisterIoCDependencyGameItemPipeline`) -> MacroCommand -> исполнение на потоке игры. Порядок шагов фиксирован, частичное состояние объекта между шагами наблюдаемо только внутри одного кванта исполнения.

Движение: `MoveGameItemCommand` читает `Position` и `Speed`, вычисляет `Position + Speed` (перегрузка оператора доменного `Vector`). Скорость хранится серверно и задаётся только в конвейере создания с клэмпингом (раздел 14.3) — клиент не может телепортировать объект.

### 3.3 Очередь команд игры

`GameCommandQueue`: `Queue<ICommand>` + флаг запечатанности.

- `Enqueue` — бросает `InvalidOperationException`, если очередь запечатана (защита контракта; маршрутизация проверяет состояние заранее, поэтому исключение — защитный барьер последней линии).
- `EnqueueTickMarker` — идемпотентен: повторный маркер по запечатанной очереди не бросает и не дублирует (исправленный дефект: первый наивный вариант ронял рабочий поток, тест `WorkerPoolTests` воспроизвёл).
- `DequeueBatch(n)` — забирает до n команд с сохранением FIFO; реализован без процедурного цикла (`Take(n).ToArray()` + удаление по счётчику).

## 4. Входной шлюз Endpoint

### 4.1 Контракт входящего сообщения (ТЗ 3.2)

```json
{
  "key": 3,
  "id": "game-1",
  "token": "1735689600.A1B2...",
  "command": "Move",
  "args": {"itemId": "ship1"}
}
```

- `key` — маршрутный hash рабочего потока; сервер возвращает актуальный `routingKey` в каждом ответе.
- `id` — идентификатор игры; до 64 символов (лимит `MaxIdentifierLength`).
- `token` — токен аутентификации или подпись (раздел 5).
- `command` — имя команды; до 64 символов.
- `args` — аргументы; сырой JSON передаётся в рабочий поток без глубокой сборки (ТЗ 3.2: отложенная десериализация). Отсутствует — подставляется `{}`.

### 4.2 Конвейер `Endpoint.Accept`

| Шаг | Операция | Стоимость | Отказ |
|-----|----------|-----------|-------|
| 1 | Проверка размера пейлоада (`MaxPayloadLengthBytes` = 65536) | O(1) | `PayloadTooLarge` |
| 2 | Поверхностный парс заголовка (`InboundMessageParser`, System.Text.Json) | O(длина заголовка) | `MalformedMessage` |
| 3 | Аутентификация (`IAuthenticator`) | O(1) / O(каноническая строка) | `AuthenticationFailed` |
| 4 | Лимит per-game (`IGameRateLimiter.TryAdmit`) | O(1) | `RateLimited` |
| 5 | Маршрутизация (`PrimaryRouter.ResolveTarget`) | O(1) | — |
| 6 | Запись в очередь (`TryWrite`) | O(1), без блокировок ожидания | `WorkerQueueFull` |

Игровая логика, обращения к `Scope` и блокирующие ожидания на пути запрещены (ТЗ 3.1). Время приёма одного сообщения — единицы микросекунд (замеры раздела 15), что укладывается в требование ТЗ о единицах миллисекунд с запасом на три порядка.

### 4.3 Причины отказа

`EndpointRejectionReason`: `MalformedMessage` (битый JSON, отсутствующее поле, неверный тип/длина поля), `AuthenticationFailed`, `WorkerQueueFull`, `RateLimited`, `PayloadTooLarge`. HTTP-мэппинг транспортом: 200 (принято), 422 (любой отказ), 405 (метод), GET — статус `{"status":"running"}`.

### 4.4 Транспорт

`HttpListenerEndpointAdapter` — тонкий адаптер: префикс `http://127.0.0.1:{port}/`, фоновый поток accept-цикла, JSON-ответ в camelCase (`JsonSerializerDefaults.Web`). Управляющие исключения остановки обрабатываются типизированно (`HttpListenerException`, `ObjectDisposedException`) — ранний вариант с catch-all и discard-переменной устранён при ревизии. Порт является портом-абстракцией: ядро `Endpoint` тестируется без сети, сетевой путь покрыт одним интеграционным контуром на loopback (T9).

## 5. Аутентификация и целостность сообщений

### 5.1 Whitelist-токены

`WhitelistTokenAuthenticator` — множество допустимых токенов (`FrozenSet`, `StringComparer.Ordinal`). Базовый режим для внутренней сети и тестов. Порт `IAuthenticator.IsAuthenticated(InboundMessage)` принимает всё сообщение, а не только токен — это позволило реализовать подпись, покрывающую всё содержимое пакета.

### 5.2 HMAC-подпись (цифровая подпись из ТЗ 3.2)

`HmacMessageAuthenticator` — HMAC-SHA256 по рекомендациям из открытых источников (SHA256 обязателен, временная метка в подписи, окно анти-replay):

- Формат токена: `{unixSeconds}.{hex(hmacSha256)}`.
- Каноническая строка: `{unixSeconds}|{routingKey}|{gameId}|{commandName}|{commandArguments}` — подпись покрывает маршрут и содержимое, изменение любого поля инвалидирует подпись.
- Окно анти-replay: `SignatureTimestampWindowSeconds` = 300 секунд в обе стороны (компенсация рассинхронизации часов; бустрап для полноценной защиты — nonce-кэш, раздел 19).
- Сравнение подписей — `CryptographicOperations.FixedTimeEquals` (защита от timing-атак).
- Метод `Sign(InboundMessage)` — минт токена для доверенных клиентов и тестов.

Фактор-классы тестов (`HmacMessageAuthenticatorTests`, 11 кейсов): валидная подпись; подмена `args`; подмена `key`; другой секрет; пять классов некорректных токенов; граница окна ровно 300 с (принято), 301 с (отклонено), будущее время в пределах окна (принято), выход за окно после хода часов (отклонено); валидация конструкторов.

## 6. Первичный роутер

### 6.1 Кодогенерация диспетчеризации (ТЗ 3.3)

`GeneratedRouterDispatcher` строит в рантайме делегат `Func<int, IMessageQueueWriter<InboundMessage>>` через `System.Linq.Expressions`:

```
table[(uint)routingKey % (uint)K]
```

- Приведение к `uint` устраняет ветвление для отрицательных ключей; экстремумы `int.MaxValue`/`int.MinValue` покрыты тестами.
- Ни одного `if`/`switch` в горячем пути: чистая арифметика и индексация массива.
- `Expression.Compile` эмитирует IL при старте — единожды, стоимость компиляции несущественна; вызов скомпилированного делегата ~1-2 нс против ~5-20 нс словаря (замеры из открытых бенчмарков, раздел 20).
- Маршрутизация O(1), предсказуемая для branch predictor: одна инструкция модуля и одна загрузка.

### 6.2 Двухуровневое разрешение цели

`PrimaryRouter.ResolveTarget(routingKey, gameId)`:

1. `ReshardingTable.ResolveRoute(gameId)` — переопределение решардинга (`ConcurrentDictionary`, потокобезопасно, валидация диапазона потока при `SetRoute`);
2. если переопределения нет — сгенерированный хеш-диспетчер.

Паттерн `??`/`is null` без if-каскадов; словарь запрашивается на каждое сообщение (порядка 10-20 нс), что пренебрежимо на фоне сетевого ввода-вывода.

### 6.3 Топологии (ТЗ 6.1)

Поддержаны обе конфигурации нагрузочного теста: единый общий роутер на пул потоков (`PrimaryRouter([w0..wK], table)`) и полностью изолированный роутер на поток (`PrimaryRouter([wi], table)` на каждого). Выбор — композиционный, без изменений кода.

### 6.4 IoC-интеграция

`RegisterIoCDependencyServerRouter` регистрирует фабрику `Server.Router.Create` в контейнере курса (`Ioc.Resolve<ICommand>("IoC.Register", ...)`) — зависимости роутера разрешаются через IoC, как требует ТЗ 3.3, при этом горячий путь остаётся на скомпилированном делегате (IoC-resolve на каждое сообщение исключён сознательно как цена, не дающая выигрыша).

## 7. Межпоточная очередь

### 7.1 Реализация

`BoundedMessageQueue<T>` — ограниченная очередь на ядре `System.Threading.Channels` (`Channel.CreateBounded`, `FullMode.Wait`, `SingleReader = true`, `SingleWriter = false`). Выбор примитива подтверждён исследованием: bounded Channel — стандарт высокопроизводительного producer-consumer в .NET (на нём же стандартизован Akka.NET); измеренные величины — порядка 17.7 млн операций/с end-to-end, нулевые аллокации на синхронном пути TryWrite/TryRead. Ручной ring buffer Vyukov даёт ~24-50 нс на пару Enqueue/Dequeue, но проигрывает в надёжности (задокументированные дефекты портов) и не даёт выигрыша при MPSC-профиле шлюза.

### 7.2 Инвариант заполненности (ТЗ 4.3)

Ёмкость `n`; счётчик `PendingCount` (Interlocked; инкремент строго до входа в канал, декремент после извлечения — порядок исключает инверсию и гарантирует точный ноль в состоянии покоя; транзиентная погрешность под контенцией допустима и зафиксирована как advisory-семантика).

- `0 <= count < n`: `TryWrite` возвращает `false` при `count == n` — производитель не блокируется никогда; перегрузка уходит в резервный поток (раздел 11) или отбрасывается с явной причиной `WorkerQueueFull`.
- `WriteBlocking` — единственный блокирующий вход, разрешён только резервному потоку (его роль по ТЗ 6.2 — принять блокировки на себя).

### 7.3 Разделение интерфейсов (ТЗ 4.2)

Производитель получает только `IMessageQueueWriter<T>` (`TryWrite`, `WriteBlocking`), потребитель — только `IMessageQueueReader<T>` (`WaitForMessage`, `ReadBlocking`, `DrainAllAvailable`). Попытка чтения из Endpoint или записи из потребителя невозможна на уровне компиляции (G27).

### 7.4 Залповое опустошение (ТЗ 4.3)

`DrainAllAvailable()` вычитывает всё накопленное за один проход без промежуточных блокировок. Рабочий поток вызывает его в начале каждого цикла; очередь практически всегда пуста, Endpoint не встречает отказа.

Отмена ожидания: `WaitForMessage(timeout, ct)` строит linked `CancellationTokenSource` с `CancelAfter` — управляемая остановка будит потребителя без внешних задержек (исправленный дефект: первый вариант `ReadBlocking` без токена делал `Stop` зависающим, что поймали тесты).

## 8. Рабочий поток

### 8.1 Цикл

```
пока не запрошена остановка:
    ExecuteCycle(now):                              # одна итерация
        сообщения = очередь.DrainAllAvailable()     # залповое опустошение
        маршрутизация каждого сообщения             # фаза вторичного роутера
        scheduler.ScheduleCycle(now)                # фаза диспетчеризации
        FinalizeCompletedMigrations()
        FinalizeShutdownSnapshotIfDrained()
    WaitForIncomingMessage(50 мс, ct)               # сон без busy-spin, мгновенное пробуждение каналом
```

- Неблокирующий `ExecuteCycle` доступен тестам и синхронным сценариям; блокирующее ожидание изолировано в `WaitForIncomingMessage` (ранний вариант с блокирующим `ExecuteBlockingCycle` создавал дедлок в тестах и был разделён — дефект покрыт ретроспективным разбором).
- Сбой одной команды изолирован: `ExecuteCommandSafely` в планировщике возвращает признак, счётчик `FailedCommandCount` попадает в `WorkerCycleResult`; цикл и поток живут (supervision-семантика Akka).
- Сбой самого цикла перехватывается в `RunLoop` (`RunProtectedCycle`): поток-актор не умирает от сбоя обработки (дефект «поток умирает от исключения в control-handler» пойман реальным потоковым тестом и устранён).

### 8.2 Результат цикла

`WorkerCycleResult(RoutedMessageCount, RejectedMessageCount, DispatchedCommandCount, FailedCommandCount, TerminatedGameIds)` — структурированные факты для диагностики, без эмоциональной окраски (S0).

## 9. Вторичный роутер

Маршрутизация входного сообщения (`RouteOneMessage`):

1. Управляющие команды разрешаются таблицей `FrozenDictionary<string, Func<InboundMessage, bool>>` (`Server.Resume`, `Server.Tick`, `Server.MigrateOut`, `Server.MigrateIn`) — ветвление по типу заменено словарём диспетчеризации (AGENTS 9.1).
2. Запечатанный поток (`_isSealedByTickMarker`) отклоняет клиентские команды.
3. Получатель из карты `IGameRecipient`: если это `GameProxy` — пересылка (запоздавшие пакеты после миграции); иначе игра.
4. Новая игра создаётся в пределах лимита `MaxActiveGames` (ТЗ 6.1), регистрируется в планировщике.
5. Защита от флуда: `MaxQueueLengthPerGame` (256 по умолчанию) — сверх квоты игра эвикируется с причиной `FloodQueueOverflow`.
6. Десериализация в `ICommand` через `JsonServerCommandDeserializer` — здесь, на рабочем потоке, как требует ТЗ 3.2; ошибки десериализации (`ArgumentException`, `JsonException`, `KeyNotFoundException`) дают отказ сообщения без остановки потока.
7. `NotifyCommandsQueued` включает игру в кольцо готовности.

## 10. Планировщик

### 10.1 Алгоритм (ТЗ 5.2)

`PriorityRoundRobinScheduler` держит по одному кольцу готовности на приоритет (`Queue<Game>` + множество членовства для O(1) защиты дубликатов) и реестр игр.

Цикл планирования `ScheduleCycle(now)`:

```
1. Watchdog: игры в await дольше MaxExternalAwaitDuration (5 мин) — завершение (Unregister + наблюдатель).
2. Кольцо High: снимок кольца, очистка, для каждой игры — ServeGame.
3. Кольцо Normal: аналогично.
```

`ServeGame`:

- Игра исключена — пропуск (защита от зомби-записей в снимке кольца).
- Token bucket: `TryAdmit(gameId, now)`; отказ — игра переносится в хвост кольца (дросселирование на цикл, не голодание).
- `DequeueBatch(CommandQuantumPerGameActivation)` (8 по умолчанию, 64 в нагрузочных конфигурациях) — квант команд.
- Исполнение с изоляцией сбоев.
- Если остались команды и игра не в await — в хвост кольца (Round-Robin).

Свойства: High-игры обслуживаются раньше Normal в каждом цикле, при этом Normal-игры получают квант каждый цикл — бесконечное голодание невозможно (длины всех активных очередей гарантированно уменьшаются, ТЗ 5.2). Сложность цикла O(число готовых игр); пустые очереди не сканируются — попадают в кольцо только при появлении команд и покидают при опустошении.

### 10.2 Состояние await

`Game.SuspendForExternalEvent(now)` переводит игру в ожидание внешнего события; `NotifyCommandsQueued` не включает await-игру в кольцо; возврат — командой `Server.Resume` (обработчик снимает флаг и возвращает игру в ротацию) — семантика Akka-почтового ящика suspend/resume. Watchdog снимает показания через инжектируемый `TimeProvider`/аргумент времени — детерминизм тестов (T8: без monkey-patching системных часов).

### 10.3 Token bucket (ТЗ 5.2, rate limiting)

`CommandRateLimiter`: на игру — ёмкость `RateLimitBucketCapacity` (16 по умолчанию), пополнение `RateLimitTokensPerSecond` (64/с), ленивое пополнение `O(1)` по формуле `min(capacity, tokens + elapsed * rate)`; отрицательный elapsed (уход часов назад) клэмпится нулём — покрыто тестом. Лимитер ограничивает число активаций игры за цикл; квант ограничивает команды за активацию — двухуровневая квота команд от одной игры за цикл.

### 10.4 Watchdog

Игры в состоянии await дольше порога завершаются превентивно: `Unregister` + `IGameTerminationObserver.NotifyGameTerminated(gameId, WatchdogAwaitTimeout)` — освобождение Scope и очереди (ТЗ 5.2). Границы порога проверены тестами: ровно 5 мин — игра жива, 5 мин + 1 мс — завершена (T1, граничные значения).

## 11. Решардинг и миграция

### 11.1 Три компонента (ТЗ 6.2)

1. **Таблица решардинга** `ReshardingTable`: `ConcurrentDictionary<gameId, threadId>`, валидация диапазона, `Snapshot()` для диагностики. Обновляется координатором ДО отправки `MigrateOut` — новые пакеты идут сразу в целевой поток.
2. **Proxy**: `GameProxy(gameId, targetWriter, overflowSink)` остаётся в карте получателей источника под тем же `gameId`. Запоздавшее сообщение: `TryWrite(target)` при успехе; иначе `overflowSink.Overflow(message, target)` — прокси никогда не блокируется.
3. **Резервный поток** `BackupTransitThread`: собственная bounded-очередь конвертов (8192), `Overflow` пишет блокирующе (его роль — принимать ожидания), поток-потребитель проталкивает конверты `WriteBlocking` в целевые очереди по мере освобождения слотов. Анализ Дейкстры (обедающие философы): циклическое ожидание A -> B и B -> A при полных очередях разорвано тем, что рабочие потоки выполняют только неблокирующие `TryWrite`; единственный блокирующий участник вынесен в выделенный поток без собственных игр — deadlock/livelock между рабочими потоками невозможен структурно.

### 11.2 Алгоритм миграции между потоками (ТЗ 7.2, этап «локально»)

`GameMigrationCoordinator.BeginThreadMigration(gameId, sourceThreadId, targetThreadId)`:

1. `reshardingTable.SetRoute(gameId, targetThreadId)`.
2. `TryPost(sourceThreadId, Server.MigrateOut {targetThreadId})` — управление уходит на поток-владелец (чужой поток не трогает чужое состояние).

На потоке-источнике (`HandleMigrateOutMessage`):

3. Очередь игры запечатывается маркером `Tick`, игра помечается мигрирующей (`_migratingTargetByGameId`).

На последующих циклах (`FinalizeCompletedMigrations`) — когда очередь запечатана и пуста:

4. Снимок: `CaptureSnapshot(game)` — все объекты Scope с типизированной сериализацией свойств (Vector -> массив, string, int) в `GameSnapshot`.
5. `Unregister(gameId, GameTransferred)`; карта получателей: вместо игры — `GameProxy`.
6. `Server.MigrateIn {snapshot}` в очередь целевого потока; при переполнении — в резервный поток.

На потоке-приёмнике (`HandleMigrateInMessage`):

7. Восстановление `Game` из снимка (Scope заново, объекты с типизированными свойствами), `Register` в планировщике, карта получателей. Игра продолжает исполнение; клиент получает новый `hash` в ответе Endpoint (переопределение уже в таблице).

Отказ целевого потока (нет в пуле): `ResolveWriter` бросает `KeyNotFoundException`, перехватывается, миграция остаётся в состоянии «в полёте» и повторяется на следующих циклах — потеря исключена, повтор идемпотентен благодаря маркеру запечатанности.

Расширение до межсерверной миграции: тот же алгоритм, где `TryPost` заменяется транспортным портом (сериализованный снимок уже переносим) — зафиксировано как этап 2 в разделе 19.

## 12. Жизненный цикл

### 12.1 Маркер Tick (ТЗ 7.1)

- Глобальный (`args` без `gameId`): поток запечатывается, все игры потока получают маркер, новые клиентские команды отклоняются; управляющие сообщения продолжают обрабатываться (нужны для остановки/миграции).
- Точечный (`args.gameId`): запечатывается одна игра.
- После маркера команды до маркера штатно исполняются — граница согласованности.

### 12.2 Soft Stop / Hard Stop (ТЗ 7.1)

`ServerShutdownCoordinator.SoftStop()`:

1. Постинг глобального Tick во все потоки пула.
2. Опрос с интервалом 20 мс до дедлайна `softStopTimeout`: каждый поток переходит в `IsShutdownCompleted` — финализатор `FinalizeShutdownSnapshotIfDrained` снимает снимки всех игр потока в `ISnapshotStore` (InMemorySnapshotStore; словарь по gameId — повторный снимок идемпотентен) после полного дрена команд и отсутствия незавершённых миграций.
3. Успех: `ServerShutdownResult(true, snapshotCount)`, пул останавливается.
4. Таймаут: автоматический переход `HardStop()` — немедленная остановка потоков без дрена (блокировки будятся токеном), результат `(false, snapshotCount)`.

Таймауты и время — через инжектируемый `TimeProvider` (DIP уровня 2 AGENTS); валидация положительного таймаута в конструкторе.

## 14. Защита от DDoS и читов

Модель угроз и механизмы (принципы: не доверять клиенту, ограничивать частоту, проверять правдоподобность — по результатам исследования, раздел 20):

### 14.1 Контур DDoS

| Угроза | Механизм | Точка | Параметры |
|--------|----------|-------|-----------|
| Гигантский пакет (парсер-амплитификация) | лимит размера пейлоада | Parser, шаг 1 | 65536 байт; сверх — `PayloadTooLarge`, парсинг не выполняется |
| Бомба идентификаторов (память) | лимит длины `id`/`command` | Parser | 64 символа; границы 64/65 покрыты тестами |
| Некорректный трафик | аутентификация до маршрутизации | Endpoint, шаг 3 | Whitelist или HMAC |
| Флуд командами на одну игру | per-game token bucket на входе | Endpoint, шаг 4 | `CommandRateLimiter`, отказ `RateLimited` до попадания в очередь |
| Флуд командами в очереди игры | эвикция по длине очереди | Worker, шаг 5 | `MaxQueueLengthPerGame` = 256, причина `FloodQueueOverflow` |
| Монополизация потока игрой | квант + token bucket активаций | Scheduler | квант 8/64, bucket 16 @ 64/с |
| Переполнение входной очереди потока | bounded-очередь + неблокирующий отказ | Thread-safe Queue | ёмкость 4096, отказ `WorkerQueueFull` без блокировки |
| Исчерпание сессий | лимит активных игр | Worker | `MaxActiveGames` = 4096 |
| Зависшие await-сессии | watchdog | Scheduler | 5 мин, превентивное завершение |
| Переполнение при пересылке | резервный поток | Resharding | transit-очередь 8192 |

Отказы по всем причинам возвращают структурированный `EndpointRejectionReason` — клиент получает явную причину, система — наблюдаемость без исключений на горячем пути.

### 14.2 Целостность

HMAC-подпись покрывает маршрут и аргументы (раздел 5.2): подмена поля, повтор пакета за пределами 300-секундного окна и подпись чужим секретом отклоняются; сравнение подписи — за константное время. Компромисс зафиксирован: nonce-кэш для полной анти-replay защиты требует внешнего хранилища и отнесён к разделу 19.

### 14.3 Анти-чит (plausibility validation)

- Скорость и координаты при создании объекта клэмпятся серверно: `MaxSpeedMagnitude` = 100, `MaxCoordinateMagnitude` = 10000 — клиентский пакет не может задать «телепорт» или отрицательные бесконечные координаты; границы ровно на лимите сохраняются, сверх — клэмп (тесты на оба класса).
- Само движение детерминировано серверным состоянием: `Move` не принимает смещение, а применяет сохранённую `Speed` — классический server-authoritative подход, клиент управляет только намерением.
- Повторная регистрация объекта с тем же `id` невозможна (`Scope.Register` — `InvalidOperationException`, сбойная команда изолируется счётчиком).

## 16. Модель потоков и памяти

Владение состоянием:

| Структура | Поток-владелец | Синхронизация |
|-----------|----------------|---------------|
| `Scope`, `GameItem`, `GameCommandQueue` | поток игры | отсутствует (ТЗ 2.3) |
| карты `GameWorker` | поток воркера | отсутствует |
| кольца планировщика | поток воркера | отсутствует |
| `BoundedMessageQueue` | разделяемая | Interlocked + семантика канала |
| `ReshardingTable` | разделяемая | `ConcurrentDictionary` |
| `InMemorySnapshotStore` | разделяемая | `ConcurrentDictionary` |

Порядки доступа: запись в канал -> инкремент строго до записи; чтение -> декремент после извлечения. Памятные барьеры поставляются каналом (Release/Acquire семантика семафоров канала). Фоновые потоки — background, управляемая остановка через `CancellationTokenSource`; блокирующие ожидания конечны либо отменяемы.

Мутабельность внутри акторов — осознанное решение домена (операция 1 Модели Акторов); все кросс-поточные DTO (`InboundMessage`, `WorkerCycleResult`, `GameSnapshot`, `TransitEnvelope`, `EndpointResponse`) — неизменяемые records.

### 17.3 Соответствие T1-T9

T1 — матрица выше; T2 — все ветви обработчиков отказов покрыты; T3 — параметризованные проверки границ (`Theory`); T4 — ни одного skip; T5 — вырожденные состояния (пустая очередь, 1 слот, экстремумы int, дубликаты, пробельные строки); T6 — дефекты (дедлок остановки, двойной Tick, инверсия счётчика, зависание BlockingCycle) воспроизведены тестами до исправления; T7 — AAA, имена `Method_Scenario_ExpectedResult`; T8 — время и сеть изолированы портами (`TimeProvider`, `IGameRateLimiter`), приватное не вскрывается; T9 — память/детерминизм, сеть только в помеченном интеграционном контуре.

## 19. Ограничения и направления развития

1. Межсерверная миграция: транспортный порт поверх `GameSnapshot` (снимок уже сериализуем; этап «локально» полностью реализован и протестирован).
2. Полная анти-replay защита HMAC: nonce-кэш во внешнем хранилище на окно 300 с (сейчас окно отсекает большинство повторов, но не все в пределах окна).
3. Watchdog O(игр) за цикл: при десятках тысяч await-игр — иерархическое timing-wheel (Varghese, Lauck) c O(1) тиками.
4. Эвикция флуд-игр без повторного воссоздания: карантин идентификатора на T секунд (сейчас спамер может немедленно пересоздать сессию).
5. Персистентность снимков: `ISnapshotStore` за файловое/сетевое хранилище.
6. Метрики: экспорт `WorkerCycleResult`/`WorkerStatistics` в Prometheus-совместимый эндпоинт.

## 21. Горячий путь: пошаговый разбор

Путь одного пакета от сокета до изменения состояния игры, с оценками:

| Шаг | Операция | Оценка времени | Комментарий |
|-----|----------|----------------|-------------|
| 1 | HTTP-чтение тела (транспорт) | доминирует сетевой I/O | вне архитектурного контроля; адаптер тонкий |
| 2 | Проверка размера | O(1), подсчёт байт | 65536 отсечка |
| 3 | `JsonDocument.Parse` заголовка | ~1-3 мкс для типичного пакета | глубина <= 64 (системный лимит), отсечка depth-бомб |
| 4 | Извлечение 4 полей + raw args | ~0.2 мкс | TryGetProperty без исключений |
| 5 | `IsAuthenticated` (whitelist) | ~20 нс | FrozenSet lookup |
| 5а | `IsAuthenticated` (HMAC) | ~1.5 мкс | HMAC-SHA256 + hex; для защищённого контура |
| 6 | `TryAdmit` лимитера | ~30 нс | dictionary + арифметика |
| 7 | `ResolveTarget` | ~25 нс | словарь решардинга + сгенерированный делегат (~1-2 нс) |
| 8 | `TryWrite` в канал | ~30-60 нс | Interlocked внутри канала + инкремент счётчика |
| 9 | Ответ HTTP | сетевой I/O | camelCase JSON |
| 10 | `DrainAllAvailable` (поток воркера) | ~50-100 нс на сообщение пачкой | один Wait за пачку |
| 11 | `RouteOneMessage` | ~100-300 нс | словарь получателей + `JsonCommand`-десериализация только здесь |
| 12 | `ServeGame` (команда) | ~50 нс оверхед + доменная логика | bucket admit + batch + исполнение |

Суммарно архитектурный оверхед на сообщение (без транспорта) — порядка 1-2 мкс; замеренный end-to-end прогон даёт ~5 мкс на сообщение при полном конвейере с реальными потоками и Channel-очередями (20000 сообщений за ~0.10 с).

Узкие места и их устранение по построению: (а) блокировки — вынесены в Channel и резервный поток; (б) IoC-resolve — исключён из горячего пути; (в) исключения — не используются как управление потоком на горячем пути (только защитные барьеры); (г) аллокации — DTO-records на границах, переиспользование буферов канала.

## 22. Разбор устранённых дефектов (case studies)

### 22.1 Дедлок управляемой остановки

Симптом: тест `WorkerThreadHostTests` подвисал; `Join()` не возвращался. Диагноз: `Stop()` отменял токен, но читатель стоял в `ReadBlocking()` без токена — поток оставался заблокированным навсегда. Исправление: токен прокинут в порт чтения (`WaitToReadAsync(ct)`); добавлен тест `ReadBlocking_ThrowsOperationCanceledException_WhenCancellationTokenIsCancelled`. Урок: каждая блокирующая операция обязана принимать токен отмены (T6: тест воспроизведён до исправления).

### 22.2 Смерть рабочего потока на повторном Tick

Симптом: хост тестов аварийно завершился; трассировка — `InvalidOperationException` из `Enqueue` в control-handler'е на фоновом потоке. Диагноз: глобальный Tick по игре, уже запечатанной точечным Tick, бросал исключение внутри `EnqueueTickMarker`; необработанное исключение в `RunLoop` убивало поток. Исправления: идемпотентный `EnqueueTickMarker`; контроль запечатанности на маршрутизации (команды к запечатанной игре отклоняются без исключения); `RunProtectedCycle` — изоляция сбоя цикла. Урок: управляющие команды обязаны быть идемпотентными, поток-актор — переживать любой сбой обработки.

### 22.3 Инверсия счётчика очереди

Симптом: `PendingCount` после квитанции всех потоков был больше нуля. Диагноз: инкремент выполнялся после `TryWrite`, декремент читателя мог обогнать его — вечный +1 на инверсии. Исправление: инкремент строго до входа в канал (с откатом при отказе) — точный ноль в покое доказан тестом `PendingCount_ReturnsToZero_AfterConcurrentProducersAndConsumerComplete`. Урок: порядок счётных операций относительно точки невозврата критичен.

### 22.4 Двойная роль неблокирующего цикла

Симптом: повторный `ExecuteCycle` в тестах блокировался навсегда — внутри был фолбэк на блокирующее чтение «при простое». Диагноз: смешение фаз (маршрутизация + ожидание) в одном методе. Исправление: `ExecuteCycle` — чистый дрен+диспетчеризация; ожидание вынесено в `WaitForIncomingMessage(50 мс, ct)` цикла хоста. Урок: CQS для фаз жизненного цикла; «ожидание» — не «обработка».

### 22.5 Ошибка кодированных ожиданий в тестах кванта

Симптом: `DispatchedCommandCount` 1 вместо 3 при Move к несуществующему объекту. Диагноз: счётчик учитывает успешно исполненные команды; две команды падали (отсутствие объекта) и считались в `FailedCommandCount`. Исправление: ожидания теста приведены к контракту (1 успешная + 2 сбойных). Урок: имена счётчиков зафиксированы контрактом `WorkerCycleResult` и не допускают двойного толкования (N1/T7).

## 26. Машины состояний

### 26.1 Состояния игры

```
                создание (первое сообщение)
                    |
                 [Ready] <----------------------+
                    |  команды в очереди        |
                    v                           |
              [Dispatching] -------------------+   (остаток очереди -> хвост кольца)
                    |  Suspend-команда
                    v
               [Awaiting] --Resume/таймаут-------+
                    |
                MigrateOut (Tick)
                    v
             [MigratingOut] --дрен+снимок--> [Migrated]  (на источнике остаётся Proxy)
                                                    |
                                             Server.MigrateIn
                                                    v
                                                 [Ready]  (на целевом потоке)

   Terminate (watchdog/флуд): из Ready/Awaiting/MigratingOut -> [Terminated] (Scope освобождён)
   Seal (Tick): ортогональный флаг очереди; запечатанная Ready-игра доигрывает хвост и замирает
```

Переходы выполняются только потоком-владельцем; атомарность обеспечивается однопоточностью фаз.

### 26.2 Состояния рабочего потока

```
[Running] --Tick(глобальный)--> [Sealed] --дрен всех игр--> [SnapshotSaved] --IsShutdownCompleted--> [Drained]
[Running] --Stop()/cancel--> [Stopped]          (из любого состояния)
[Running] --фатальный сбой--> [Running]          (RunProtectedCycle: изоляция)
```

### 26.3 Состояния миграции одной игры

```
[Idle] --MigrateOut--> [Sealing: Tick в очереди] --очередь пуста и запечатана--> [Transferring: снимок]
[Transferring] --Unregister+Proxy+MigrateIn--> [Idle]  (успех)
[Transferring] --ResolveWriter отказал--> [Sealing]    (повтор на следующем цикле)
```

### 27.2 Сценарий: массовая миграция (thundering herd)

Переконфигурация пула на N потоков порождает волну миграций. Сглаживание по построению: (а) каждая миграция занимает один слот очереди целевого потока, барьер Tick гарантирует минимальный снимок; (б) при заполнении целевой очереди снимки уходят в резервный поток, не блокируя источники; (в) миграции сериализуются на потоке-владельце — лавины блокировок невозможны.

### 27.3 Сценарий: спам-клиент после эвикции

Эвиция освобождает ресурсы; повторное воссоздание сессии тем же `gameId` возможно, но каждая новая волна флуда вновь упирается в пер-игровой лимит входа и лимит очереди, не затрагивая соседние игры потока. Карантин идентификатора зафиксирован как развитие (раздел 19.4).

## 28. Профиль памяти

- Сообщение в системе: один экземпляр `InboundMessage` (record, 5 ссылок/полей) от Endpoint до игры; дополнительных копий нет — снимок Scope создаётся только при миграции/остановке.
- Очередь: предвыделенные сегменты bounded-канала; `DrainAllAvailable` аллоцирует один список на пачку (пачка — типичная единица цикла).
- Планировщик: снимок кольца — один массив за цикл на ярус; O(готовые) ссылок, без аллокаций на команду.
- Счётчики и статистика: только примитивы; `WorkerStatistics` — 4 int на поток по запросу.
- GC-давление: нулевые аллокации на сообщении в установившемся режиме (кроме списка дрена и результата цикла, амортизируются на пачку); детерминированное освобождение снимков — вне горячих путей.

- Добавить рабочий поток: `workerPool.StartWorker()`; перебалансировка — серия `GameMigrationCoordinator.BeginThreadMigration` (снимки уйдут через Proxy без остановки).

## 33. Планировщик: полный алгоритм

### 34.1 Псевдокод цикла

```
ScheduleCycle(now):
    terminated = []
    для каждой game из реестра, где game.awaiting и game.AwaitDuration(now) > MaxExternalAwaitDuration:
        Unregister(game.id, WatchdogAwaitTimeout); terminated += game.id

    dispatched = DispatchRing(highRing, now) + DispatchRing(normalRing, now)
    return ScheduleOutcome(dispatched.ok, dispatched.failed, terminated)

DispatchRing(ring, now):
    snapshot = ring.ToArray(); ring.Clear()
    для каждого game из snapshot: снять из множества членовства
    результаты = snapshot.Select(g => ServeGame(g, now, ring))
    return (сумма успешных, сумма сбойных)

ServeGame(game, now, ring):
    если game.id отсутствует в реестре: return (0, 0)          # зомби-защита
    если не rateLimiter.TryAdmit(game.id, now):                  # дросселирование на цикл
        ring.EnqueueBack(game); return (0, 0)
    batch = game.queue.DequeueBatch(quantum)                     # FIFO, до quantum команд
    для каждой command из batch:
        try command.Execute() -> ok; catch -> failed             # изоляция сбоев
    если game.queue не пуста и не game.awaiting:
        ring.EnqueueBack(game)                                   # Round-Robin уступка
    return (ok, failed)
```

### 34.2 Инварианты и деградации

- Игра присутствует не более чем в одном кольце и не более одного раза (`_readyGameIds`).
- Включение в кольцо — только при наличии команд и отсутствии await; исключение — при опустошении или переходе в await.
- Все ярусы проходятся за один цикл: при бесконечном потоке High-команд Normal-игры получают свой квант каждый цикл (свойство, проверенное трёхцикловым тестом).
- Тест деградации: при `refill = 0` и ёмкости 2 игра обслуживается два цикла, затем пропускается до пополнения — устойчивая деградация без голодания соседей.
- Watchdog за цикл — O(игр); при десятках тысяч игр рекомендуется переход на timing wheel (раздел 19.3).

## 34. Протокол: правила полей и форматы

### 35.1 Правила полей запроса

| Поле | Тип JSON | Ограничения | Ошибки |
|------|----------|-------------|--------|
| `key` | number | целое, вмещается в int32 | отсутствует / не число / вне int32 -> `MalformedMessage` |
| `id` | string | длина 1..64 | отсутствует / не строка / вне длины -> `MalformedMessage` |
| `token` | string | формат аутентификатора | невалид -> `AuthenticationFailed` |
| `command` | string | длина 1..64; известное имя проверяется на рабочем потоке | неизвестное -> отклонение потоком (счётчик Rejected) |
| `args` | любой JSON | размер в пределах пакета; глубина <= 64 (системный лимит) | depth bomb -> `MalformedMessage` |
| пакет | object | размер <= 65536 байт UTF-8 | `PayloadTooLarge` |

### 35.2 Формат снимка

```json
{
  "gameId": "game-1",
  "priority": "Normal",
  "items": [
    {
      "itemId": "ship1",
      "properties": { "Type": "Ship", "Position": [1, 2], "Speed": [0, 1] }
    }
  ]
}
```

Правила кодирования свойств: `Vector` -> массив int; `string` -> строка; `int` -> число; прочее -> строковое представление (только для диагностики). Кодек туда-обратно проверен тестами на обоих типах и границах.

### 35.3 Формат подписи HMAC

Токен: `{unixSeconds}.{hex(HMAC-SHA256(canonical))}`.

Каноническая строка: `{unixSeconds}|{routingKey}|{gameId}|{commandName}|{commandArguments}`.

Подпись покрывает маршрут и содержимое: подмена `key`, `args` или использование другого секрета обнаруживается (тесты). Сравнение hex-строк — `CryptographicOperations.FixedTimeEquals` (защита от timing-атак).

## 35. Сравнение с промышленными решениями

| Аспект | Orleans | Akka.NET | Proto.Actor | Данная система |
|--------|---------|----------|-------------|----------------|
| Единица изоляции | grain (turn-based) | actor (mailbox) | actor | игра = актор с личной очередью |
| Планирование | WorkItemGroup, квант активации | dispatcher + throughput deadline | batching mailbox | Priority+Round-Robin кольца + квант |
| Await-исключение | продолжения на scheduler | suspend/resume mailbox | async mailbox | флаг await + повторное включение командой Resume |
| Очередь | внутренние очереди активаций | ChannelExecutor (стандарт на Channels) | custom mailbox | BoundedMessageQueue на Channels |
| Перенос актора | grain migration (кластер) | cluster sharding handoff | нет в ядре | Tick-барьер + снимок + Proxy + резервный поток |
| Межузловой транспорт | встроенный | встроенный | встроенный | порт для этапа 2 (снимок уже сериализуем) |
| Контроль остановки | coordinated shutdown | coordinated shutdown | — | Tick + SoftStop(таймаут)->HardStop + снимки |

Вывод: ключевые механизмы соответствуют практикам зрелых фреймворков; отличия — целевая специализация под пошаговые игры (пер-игровые очереди, игровой watchdog, серверные приоритеты платящих сессий) и прозрачность реализации.

## 36. Наблюдаемость

Структурированные факты без эмоциональной окраски (S0):

- Результат цикла воркера: `routed=.. rejected=.. dispatched=.. failed=.. terminated=..`.
- Статистика пула: `thread=.. games=.. pending=.. queuedCommands=..`.
- Завершения игр: `gameId=.. reason=WatchdogAwaitTimeout|FloodQueueOverflow|GameTransferred`.
- Миграции: `gameId=.. from=.. to=.. snapshotBytes=..`.
- Отказы Endpoint: причина из `EndpointRejectionReason` + метрика частоты по причинам.

Рекомендуемые алерты: устойчивый рост `RejectedMessageCount` (флуд/сбой клиента), рост `PendingInputMessages` (перегрузка потока), частые `FloodQueueOverflow` (атака), `CompletedGracefully=false` (деградация остановки).

## 37. Защита инженерных решений

| Вопрос | Ответ |
|--------|-------|
| Почему Channels, а не hand-rolled Vyukov MPMC? | Vyukov даёт ~24-50 нс на пару операций, но в профиле MPSC шлюза выигрыша не даёт; порты C# имели задокументированные дефекты; Channels — стандарт (Akka.NET перешёл на ChannelExecutor), нулевые аллокации, встроенная отмена ожидания |
| Почему Expression.Compile, а не Roslyn-компиляция как в AdapterGenerator? | диспетчер — одно выражение-индексация: Compile дешевле и быстрее полного Roslyn-ассемблирования; Roslyn оставлен там, где генерируются типы (адаптеры) |
| Почему словарь решардинга запрашивается на каждое сообщение? | 10-20 нс на ConcurrentDictionary против сетевого ввода-вывода; встраивание переопределений в сгенерированную таблицу требует перекомпиляции на каждую миграцию |
| Почему TimeProvider, а не DateTime.UtcNow? | DIP уровня 2: детерминированные тесты watchdog/подписи/лимитера без monkey-patching |
| Почему FrozenDictionary, а не switch? | вариативность по ключам расширяется (control-commands), таблица диспетчеризации — предписанное замещение ветвлений (AGENTS 9.1) |
| Почему records на границах? | неизменяемые DTO между потоками: безопасная публикация, отсутствие гонок по содержимому |
| Почему обычный Dictionary внутри игры? | инвариант ТЗ 2.3: монопольный доступ потока-владельца; синхронизация была бы чистым оверхедом |
| Почему квант в командах, а не в миллисекундах? | детерминизм тестов и предсказуемость длин очередей; временной бюджет добавляется тривиально поверх (Stopwatch-проверка в ServeGame) |
| Почему эвикция, а не отбрасывание хвоста очереди? | отбрасывание молча теряет команды; эвикция освобождает память и даёт явную причину наблюдателю |
| Почему приоритет через кольца, а не DRR? | требование ТЗ — отсутствие голодания; проход всех ярусов за цикл даёт его без сложностей кредитов; DRR — оптимизация при неоднородной стоимости команд |

## 38. Типовые сценарии отказа и поведение системы

| Сценарий | Поведение | Восстановление |
|----------|-----------|----------------|
| Клиент шлёт битый JSON | `MalformedMessage`, соединение продолжает работать | бездействие клиента |
| Клиент шлёт команду неизвестного типа | сообщение отбрасывается воркером, игра живёт | клиент исправляет протокол |
| Клиент превышает частоту | `RateLimited` на входе; при продолжении — эвикция очереди | токены восстанавливаются со временем |
| Игра падает в вечный await | watchdog завершает через 5 минут | клиент переподключается |
| Целевой поток миграции отсутствует | миграция остаётся в полёте, повторяется каждый цикл | появление потока завершает перенос |
| Очередь потока переполнена | отказ `WorkerQueueFull`, производитель не блокируется | дрен потоком освобождает слоты |
| Исключение в команде игры | счётчик `FailedCommandCount`, цикл продолжается | фиксы на уровне домена |
| Soft Stop не успевает | автоматический Hard Stop, снимки частично сохранены | перезапуск с последнего снимка |
| Поток умирает от внешней причины | background-поток; пул фиксирует отсутствие | перезапуск `StartWorker` + миграции |
